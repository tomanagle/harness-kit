# Lifecycle hooks

Hooks extend session creation and turn preparation without replacing the kit's
session manager. The core accepts an injected `hooks.Registration` interface;
the default registry also supports handlers owned by connected TypeScript and Go
clients. Check `server.capabilities.hooks` when connecting to older sidecars.

## TypeScript

Register handlers before creating or prompting the sessions that need them:

```ts
const remove = await kit.hooks.register(
  "turn.before",
  async (context) => {
    if (!context.isFirstTurn) return;
    const text = await loadProjectContext(context.session, context.signal);
    return {
      input: [...context.input, { type: "text", text }],
    };
  },
  { id: "project-context", order: 10 },
);

await kit.settings.configure({
  patch: {
    hooks: {
      enabled: true,
      timeoutMs: 10_000,
      maxConcurrent: 32,
      onError: "fail",
      required: ["project-context"],
    },
  },
});

// Later, when this integration is deliberately removed:
await kit.settings.configure({ patch: { hooks: { required: [] } } });
await remove();
```

`loadProjectContext` is application code. `context.signal` aborts when preparation
is cancelled, its deadline expires, or the connection ends. `register` returns an
async disposer; `kit.hooks.list()` lists registrations across connections. Supply
`sessionId` to scope a turn hook to one session. Handler IDs must be unique across
the host. Anonymous IDs are generated by the TypeScript helper.

## Lifecycle and mutation

| Hook                   | Context                                                               | Returned changes                                             |
| ---------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------ |
| `session.beforeCreate` | Effective creation request in `create`                                | `{ create: { ...context.create, title, metadata, config } }` |
| `turn.before`          | Session, prompt input, requested config patch, turn ID, `isFirstTurn` | `{ input, config }`                                          |
| `turn.after`           | Session, input, turn ID, result, `isFirstTurn`                        | Empty response; perform application work in the handler      |

Before-create runs after startup defaults are merged and before runtime creation.
The existing Go `Prepare` callback runs afterward. Restore preserves saved
configuration and does not call before-create. Forks inherit their parent's
configuration; their first local prompt passes through `turn.before`.

Before-turn finishes before turn admission. Returned model, effort and native
options pass normal capability and host-policy validation. It cannot change the
session's identity, working directory or defaults. Input replaces the entire
input array; config patches merge by field. A later hook's set/reset wins over
an earlier change to that field. Returning nothing preserves the request.

`isFirstTurn` uses the persisted accepted-turn count, excluding inherited turns
on a fork. It remains true after rejected preparation, becomes false after the
first admitted turn (even if the agent later fails), and survives restore.
Reusing an already-admitted turn ID is rejected before hooks run. A rejected
attempt can retry its ID; hooks may therefore run again. `invocationId` combines
the session ID, turn ID, phase and hook ID for application deduplication. Supply
a stable `turnId` when retrying. Before-create IDs identify creation attempts,
not retries of an externally defined operation. External effects are not
transactional with session admission; make handlers idempotent where needed.

After-turn runs after the result has been published and persisted as far as the
session store permits. It is best-effort, is not replayed after a crash, and
cannot change success into failure. Its errors go to the structured log stream.
`turn.completed`, `Turn.done`, and result-only `run()` do not wait for after-turn
handlers. An after hook may rename a session or start another turn, but should
not synchronously shut down the manager that is waiting for it to finish.

## Ordering, errors and lifetime

Handlers run by ascending `order`, then lexicographic ID. The registry snapshots
matching handlers for each phase. Registration changes affect subsequent phases;
an invocation already selected may finish after unregistering. Handlers receive
owned input snapshots, run outside manager locks, and may read settings or update
session metadata. A recursive prompt on the same session during preparation
returns `session_busy`. Cancellation and close can interrupt preparation.

`settings.hooks` is global and mutable at runtime. Defaults: enabled, 30 seconds
per handler, 32 concurrently executing callbacks, and `onError: "fail"`.
`"continue"` logs a failed callback and preserves the preceding request before
continuing. Missing required registrations always fail while hooks are enabled.
Exceeding `maxConcurrent` fails that invocation rather than adding an unbounded
queue. Timeouts release the caller; Go code cannot forcibly terminate arbitrary
application code, so a handler ignoring cancellation retains its concurrency
slot until it returns. Remote clients also bound outstanding callbacks, including
callbacks that outlive a server timeout. JavaScript callbacks must honor their abort signal
and avoid blocking their event loop.

Client registrations belong to their connection. Other clients cannot replace
or remove them. Disconnect removes future registrations; in-flight reverse calls
fail. Use stable IDs in `hooks.required` if losing a handler must block new work.
Hook policy can be saved through settings persistence, but executable handlers
are registered again after startup. Reconnect and register them before prompting.

Callback failures rejecting preparation use RPC reason `hook_failed`; returned
settings still use the normal validation errors. Cancellation uses the existing
cancellation response. Hook errors/warnings are visible through the
Go `slog` stream. Hooks do not intercept native agent-internal tool execution;
use the existing approval/tool interfaces for supported tool interactions.

## Go

For an embedded manager, register a `hooks.Handler` or `hooks.HandlerFunc`:

```go
registry := hooks.NewRegistry()
err := registry.Register("application", hooks.Spec{
    ID: "project-context", Name: hooks.BeforeTurn,
}, hooks.HandlerFunc(func(ctx context.Context, request hooks.Request) (hooks.Response, error) {
    if !request.IsFirstTurn { return hooks.Response{}, nil }
    input := append(request.Input, agent.InputPart{Type: "text", Text: "Project context"})
    return hooks.Response{Input: &input}, nil
}))
if err != nil { return err }
manager := session.NewManager(runtimes, session.Options{Hooks: registry})
```

For the standalone Go client, use `RegisterHook(ctx, HookSpec, HookFunc)` and
`UnregisterHook(ctx, id)`. The generated `HookRequest`, `HookResponse`, settings,
RPC methods and reverse-call contract share the same schema as TypeScript.
